# Ads · 付费增长运营

## 入口

普通运营查数直接使用 `ads_schema` / `ads_sql`。需要配置、报告或平台操作时，再按需调用 `ads_capability_context` 发现对应能力。模型负责推理与编排，服务端负责权限、数据、指标和配置 authority。

若当前 Host 能读取 ChatGrowing MCP Resources、但没有披露依赖的自定义 Tool，先读取 `ads-contract://host-tool-fallback-v1`，再按其中的 `ads-query://execute/{tool_name}{?arguments}` Resource Template 调用同一只读能力。该入口仅用于 Host 恢复，不扩大权限，也不得绕过正常 Tool。

## 编排

1. 根据用户目标选择最小任务范围：问数、巡检、诊断、复盘、报告或配置核对。
2. 按服务端 guidance 按需组合 SQL 查询、知识、上下文与报告能力；不在 Skill 保存固定工具链、对象树、规则数量或报告路由。
3. 大范围任务先排序和分流，只对高影响对象继续补证；根据已返回数据决定下一条 SQL，不要求发布结果集。
4. 把事实、派生特征、观察、候选原因和待审批动作分层，不把数据缺口写成业务主因。
5. 输出当前结论、影响范围、证据与反证、限制、优先级、下一步和停止条件。

## 边界

- 当前授权范围是唯一数据边界；App、名称或旧配置不能扩大权限。
- 不重算正式指标，不把候选原因升级为确定因果。
- 用户明确要求创建或编辑广告时，转交当前 Gateway 的 Action capabilities 和广告创建与编辑流程（安装包提供时使用 `ads-action-operations`）；先准备精确方案，再满足该平台的真实确认门禁。分析建议本身不构成写入授权。
- 本分析编排不直接执行广告写操作，不静默修改报告、监控、动作历史或外部交付。
